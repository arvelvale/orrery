# 01 · 架构与技术路线

## 模块

OpenCode（2026-09-17）：`adapters/opencode.rs` 用 bundled rusqlite 只读事务读取 `opencode.db`，递归合并子 agent；output = tokens_output + tokens_reasoning。会话体积按 message/part/event 的 UTF-8 内容字节计，不等于可回收磁盘空间，以 time_updated 缓存到索引（版本 3）。删除入口明确拒绝。独立 SQL 与真实 Tauri invoke 的逐会话验证入口为 `scripts/verify-opencode.mjs`，仅本地保存报告/截图到忽略目录 `.orrery/`；不调用真实删除。Windows 已实测，其他平台未实测。

## 原生会话转换（2026-09-27）

首批支持 Claude Code ↔ Codex，2026-10-07 起扩展为 Claude Code、Codex、OpenCode 三家互转（见下文"结构"）。会话详情的「转换会话」和侧栏的「会话转换」进入同一张双栏核对页；仅主会话可选。`ui/app.js` 在桌面版调用 `convert_session(harness, id)`，成功后重新扫描，并给出目标原生会话 ID 与恢复入口。浏览器预览只演示虚构数据，不写磁盘。

- Claude Code → Codex：`src-tauri/src/transfer/` 先读取来源 JSONL，验证工作目录及可移植内容，再通过 Codex 官方 app-server 的 `externalAgentConfig/import` 导入。导入后的 rollout 由 Codex 自己创建；同一来源版本再次导入时返回已有目标。自定义 `CLAUDE_CONFIG_DIR` 用沙盒暂存路径供官方导入器发现，完成后移除暂存文件。
- Codex → Claude Code：合并同 ID 的主 rollout，逐条映射用户/助手消息、文本工具调用与结果、用户内嵌图片；写到目标项目目录的临时 JSONL，完成与来源稳定性检查后原子改名。工具输出保留为带标记的历史文本，不冒充用户指令；内部 reasoning 不导出。来源会话不改动。
- 保真边界：Claude 来源里的图片/文档因 Codex 官方导入器会静默丢弃，转换器明确拒绝；Codex 工具结果中的非文本媒体及未知 response item 也拒绝，避免宣称成功却缺内容。CLI 缺失、项目目录丢失、来源变化均在界面提示。此处的「完整历史」指可移植的可见对话和工具记录，不包含内部隐藏推理。
- 验证：隔离 `ORRERY_HOME` 的双向 Rust 测试创建合成会话，检验原文件不变、重复导入、图片拒绝、工具结果与用户图片；`scripts/verify-session-transfer.mjs` 用 Codex `thread/read` 和 Claude `--resume` + 回环假供应商验证目标工具确实读取到历史。桌面 WebView2 的 Tauri invoke 路径在同一沙盒实测。真实用户会话未写入，macOS/Linux 原生客户端尚待实测。

其他 harness 仍需各自的原生格式读写与目标 CLI 验证；界面只开放已验证的方向。

**结构（2026-10-07）**：每家一个读取器、每个目标一个写入器，中间统一成 `Transcript`（工作目录 + 标题 + 轮次；每轮由文本 / 图片 / 工具调用 / 工具结果片段组成，工具记录一律归助手侧，不得升级为用户指令）。加一个来源即可通往所有目标。现开放 Claude Code、Codex、OpenCode 三家互转，共 6 个方向。

| 文件 | 读取器 | 写入器 |
|---|---|---|
| `transfer/mod.rs` | — | `Transcript` 类型、来源快照（文件按长度+mtime；OpenCode 按该会话的 `time_updated`+消息数，因为库文件一有别的会话写入就会变）、`convert_to(来源, id, 目标)` 调度 |
| `transfer/claude.rs` | 沿 `parentUuid` 从最后一条消息回溯，只取生效分支（回退/改写会产生分叉）；压缩边界的 `parentUuid` 为空，回溯自然停在那里，得到"压缩摘要 + 之后"，正是 Claude 自己发给模型的内容 | 新 JSONL，临时文件写完原子改名 |
| `transfer/codex.rs` | rollout 的 `response_item`；标题取 `session_index` 的 `thread_name`，否则首条真实用户输入 | 官方 `externalAgentConfig/import`（只吃 Claude JSONL） |
| `transfer/opencode.rs` | 只读查 `message`/`part`；压缩过的从最近一次完成的压缩处开始读 | 生成导出文档交给官方 `opencode import` |

Claude Code → Codex 没有图片时不经过 `Transcript`，原文件直接交给 Codex 导入器；有图片时改走 `Transcript`（Codex 导入器会静默丢弃 Claude 文件里的图片）。其他来源去 Codex：先把 Claude JSONL 渲染进暂存目录再导入。

**图片（2026-10-07，`transfer/media.rs`）**：目标放不下的图片存成文件、原位置留路径，不再拒绝整条会话。规则：工具结果里的截图、助手发的图片，迁往任何目标都存成文件（工具记录在目标里是文字，图片没有地方放）；用户发的图片迁往 Claude/OpenCode 原样内联，迁往 Codex 存成文件。文件在 `~/.orrery/transfer-media/<转换 ID>/<n>.png`，`owner.json` 记录归属会话；转换失败整目录删除；经 Orrery 删除目标会话时按同一方式（回收站/永久）处理。放在项目目录外是有意的：不往用户仓库里塞未跟踪文件，代价是 Claude Code 交互模式下读项目外文件会弹权限确认。转换前前端调只读的 `preview_transfer` 显示张数或拒绝原因。PDF、链接形式的图片仍拒绝。

OpenCode 写入的实测结论（1.18.31，沙盒）：
- 导入**不是原子的**：缺一个字段，会在已写入会话和部分消息之后才报错，留下半条会话 → 字段一次给全；导入失败或导入后消息数对不上，立即用官方 `opencode session delete` 清掉。
- 恢复时不加 `-m` 用的是**消息里记录的模型**，写不存在的模型会直接报错 → 取用户最近一次实际用过的模型；OpenCode 里从没用过模型时拒绝并提示先用一次。
- `import` 按当前目录归项目 → 在原工作目录里运行。
- ID 需按 OpenCode 规则生成（48 位时间序前缀，消息/片段递增、会话递减），否则消息顺序会乱。
- 图片作为 `file` 片段迁移；是否真的发给模型由 OpenCode 按模型能力决定（不支持图片输入的模型会被它替换成一句说明，这是 OpenCode 自身行为）。

工作目录统一做字面规整（去掉 `.`/`..`），不用 `canonicalize`：它会把 junction/符号链接解析到目标，而 harness 在链接目录里启动时记录的是链接路径。这顺带修了第 1 步记下的"带 `..` 的路径落到另一个 Claude 项目目录"的问题。

验证：
- 单元测试 27 个（读取映射、分支/压缩、ID 顺序、导出文档字段、轮次合并、媒体规则）。
- `sandbox_bidirectional`（Claude ⇄ Codex）与新增 `sandbox_opencode_both_ways`（cc→opencode、codex→opencode、opencode→cc、opencode→codex、带图去 Codex 被拒且不留痕、导入失败的半条会话可清除、来源字节不变），均用真实 CLI。
- `scripts/verify-session-transfer.mjs` 与新增 `scripts/verify-opencode-transfer.mjs`：目标工具恢复会话后，标记词（及图片）确实出现在发往回环假供应商的请求里；OpenCode 不加 `-m` 恢复。
- Codex → Claude 的输出与重构前比对：对话内容逐字节一致，只有 `cwd` 字段因路径规整而变化。
- 只读试跑真实会话（`real_sessions_dry_run`，2026-10-07）：截图改为存文件后，可读从 Claude Code 15/32、Codex 19/55、OpenCode 37/47 升到 31/32、52/55、45/47；剩下的是空会话、缺工作目录、1 条带 PDF。桌面版预检另查工作目录是否存在：Codex → Claude 55 条里 47 条可转（5 条项目目录已不在、3 条空会话）。
- `scripts/verify-transfer-media.mjs`：回环假模型在第一轮发起读文件工具调用、指向迁移时存下的图片，Claude Code（`Read`）与 OpenCode（`read`，参数名取自它自己声明的工具清单）都执行了读取并在下一轮请求里把图片送回模型。Codex 的 `view_image` 未做同样实测。
- Codex 每条消息写两份（`event_msg` 给界面、`response_item` 给模型），统计图片引用只数 `response_item`。

后续计划：逐个加来源 Z Code → WorkBuddy → Kimi → DSH，每个都要独立脚本对账并在目标工具里实际恢复后再开放。Antigravity 作来源（protobuf 无格式定义，保真没把握）、Kimi 作目标（无 import，需直接写其存储）暂不做。

## 桌面壳技术选型（已锁定）

**采用 Tauri 2。** Agent 日常在电脑上跑，产品形态是桌面应用，不是手机 Web。

| 方案 | 优点 | 风险 | 结论 |
|---|---|---|---|
| **Tauri 2** | 包体小、Rust 适合扫盘/子进程、系统 WebView | node-pty/终端生态要自建（sidecar） | **已选定** |
| Electron | node-pty / xterm.js 成熟 | 包体大、内存高 | 仅当多窗格终端成本过高再评估 |

UI：浅色桌面三栏（侧栏导航 · 会话情报条 · 详情面板），对齐 `DESIGN.md`。  
HTML 原型（`index.html`）即 WebView 前身，同一套 DOM/交互迁入 Tauri。

## 模型代理（✅ 已实现，2026-09-16）

- 形态：本机 `127.0.0.1:8787/v1`（可配，非回环地址拒绝启动）
- 实现：axum 0.8 + tokio（独立线程跑运行时）+ reqwest（rustls，流式）；代码在 `src-tauri/src/proxy/`

| 文件 | 职责 |
|---|---|
| `mod.rs` | 启停、状态、`init()` 自启动；watch 通道优雅关闭；上报**实际**绑定端口（端口 0 时不能回显配置值） |
| `config.rs` | `Provider`/`Wire`/`ProxyConfig`，读写 `~/.orrery/proxy.json`，按前缀选供应商 |
| `server.rs` | 路由与转发：鉴权头按 wire 重建，SSE 逐块透传 |
| `state.rs` | 计数、最近一次请求与错误、运行时长 |

- 两个协议面：
  - `POST /v1/chat/completions` → OpenAI 形状，`Authorization: Bearer <key>`
  - `POST /v1/messages` → Anthropic 形状，`x-api-key` + `anthropic-version`（请求带了就沿用，否则 `2023-06-01`）
  - 另有 `GET /v1/models`（列路由表里的模型）与 `GET /health`
- 路由：请求头 `x-orrery-harness: <id>` 命中路由表就改写 `model`，不带则保留请求原值
- 供应商选择：按模型名前缀严格匹配（`claude*`→anthropic、`kimi*`→moonshot、`deepseek*`→deepseek、`gpt*`/`o*`→openai）。**匹配不到直接 503 报错**，不做「挑一个顶上」的兜底——早期实现会把 `whatever` 转给 deepseek，把 `claude-opus-5` 标成 deepseek 所有，属于会误导人的行为
- 鉴权头不透传：调用方带来的 `Authorization`/`x-api-key` 一律丢弃，由代理按目标供应商重建
- 配置示例（`~/.orrery/proxy.json`）：

```json
{
  "listen": "127.0.0.1:8787",
  "auto_start": false,
  "routes": { "cc": "claude-sonnet-4.6", "kimi": "kimi-k3" },
  "providers": {
    "anthropic": {
      "base_url": "https://api.anthropic.com/v1",
      "api_key_env": "ANTHROPIC_API_KEY",
      "wire": "anthropic",
      "model_prefixes": ["claude"]
    }
  }
}
```

- 密钥：只在转发瞬间 `std::env::var` 读，不落盘、不进日志、不回传界面；配置里只存变量**名**。未设置时返回 503 并说明缺哪个变量（集成测试断言响应体里不出现 key 值）
- 失败语义：上游状态码原样透传（429/5xx 不改写）；代理自身的错误统一为 `{"error":{"type":"orrery_proxy","message":…}}`
- 测试：`src-tauri/tests/proxy.rs` 起假上游覆盖路由改写、两种 wire 的鉴权头、SSE 分块到达时序、上游 429 透传、缺 key 503、`/health` 计数、停止；合计 11 个测试（10 单测 + 1 集成）

## 持久化解析索引（✅ 已实现，2026-09-16）

解析缓存原本只活在进程内存里，每次开应用都要把四个 harness 的日志重读一遍。现在同一张表落盘到
`~/.orrery/index.json`，启动时读回来，扫描只对 `sig` 变了的文件重新解析。

- 缓存键：Claude Code = 主 jsonl 路径，Kimi = 会话目录，DSH = v3 日志，Codex = 单个 rollout 文件
  （Codex 一个会话由多个 rollout 合并而来，缓存必须在合并之前那一层）
- `sig` = 参与解析的文件的 (路径, 长度, mtime) 折叠出的 u64，变了才重新解析
- 格式版本 `INDEX_VERSION`：`SessionSummary` / `Rollout` 改字段必须 +1，否则会读出半截数据；
  版本不符、文件损坏、读不出来，一律整份丢弃重建——索引只是缓存，不允许它让会话列表出错
- 写盘：临时文件 + rename，进程被杀不会留下半个索引；本轮没有文件被重新解析就不写
- 死条目清理：保存时剔除路径已消失的条目；**读取时也剔一遍**并标记待写盘——
  否则用户在应用外删了会话、又恰好没有别的文件变动，索引就永远不会重写，死条目一直留着
- 删除会话时 `forget_memo` 连内存和索引一起清，并立即写盘

实测（本机 188 个会话，dev 构建）：

| | 耗时 | 重新解析 |
|---|---|---|
| 无索引（首次） | 5.5s（应用内 6.4s） | 204 个文件 |
| 有索引 | 0.12s | 0 个文件 |
| 改动 1 个会话文件后 | 0.12s 级 | 1 个文件 |

## 在终端恢复会话（✅ 2026-09-17）

选中会话 → 起终端 → `cd` 到会话记录的工作目录 → 跑该 harness 自己的恢复命令。
代码在 `src-tauri/src/resume.rs`。

| harness | 命令（本机实测 `--help`） |
|---|---|
| cc | `claude --resume <id>` |
| codex | `codex resume <id>` |
| kimi | `kimi --session <id>`（id 与 kimi 自己 `session_index.jsonl` 的 `sessionId` 同形） |
| dsh | 有非 web 的 profile 时 `dsh --profile <profile> --resume <id>`；只有 web 时退为 `dsh --profile web`（打开网页界面自己挑，返回值带 `web_fallback:` 前缀，提示文案据此区分）|
| 自己登记的工具 | 不支持：不知道对方有没有 CLI |
| opencode | `opencode --session <id>` |

踩到的两个坑：

1. **DSH 的 `--resume` 不是启动器参数**，是转发给被引导的 profile 应用的。本机只装了 `web`
   profile，而 web 是浏览器 UI、没有 `--resume`。所以要先看装了什么 profile，只有非 web 的
   才谈得上在终端恢复，否则给出专门的提示而不是笼统报错。
2. **Windows 上扩展名的查找顺序会决定成败**：npm 同时装 `codex`（bash shim）和 `codex.cmd`。
   先试无扩展名的话，`CreateProcess` 会"成功"地起一个立刻失败的进程——终端一闪而过，
   而代码这边 `spawn()` 返回 Ok，界面还提示恢复成功。顺序必须是 `.exe` → `.cmd` → `.bat` → 无扩展名。
   这个 bug 骗过了返回值，只能靠"去进程表里确认新进程真的存在"才抓得住。

终端选择：优先 Windows Terminal（`wt -d <cwd> <程序> <参数…>`），没有就退回
`cmd /c start "" cmd /k`；macOS 用 `open -a Terminal` 跑一个临时 `.command` 脚本，
Linux 依次试 `x-terminal-emulator` / `gnome-terminal` / `konsole` / `xfce4-terminal` /
`alacritty` / `xterm`。只有 Windows 路径实测过。

安全：id 过白名单（字母数字 + `-_`，8–80 字符），工作目录由后端从扫描结果给出、
不接受前端任意路径，参数按数组传给进程。实测通过：Codex 与 Kimi 都真的拉起了进程，
命令行分别是 `codex.exe resume <uuid>` 和 `kimi.exe --session session_<uuid>`，
Kimi 那条的工作目录还含中文。

## Z Code 的用量口径（2026-09-18 实测）

Z Code 也是 OpenCode 系（`session`/`message`/`part` 同源），但它记账比 OpenCode 细得多：
`model_usage` 每次 API 调用一行，`turn_usage` 每轮一行。

- **以 `model_usage` 为准**。两张表在两个会话里差一次调用，查 `query_source` 发现是 60 次
  `main_turn` + 2 次 `session_title`——`turn_usage` 不记标题生成这类副调用，但它们同样花钱。
- **`input_tokens` 已经包含缓存命中**（OpenAI 口径）。62 行全部满足
  `computed_total_tokens = input + output`，供应商原始返回
  `{inputTokens:33032, outputTokens:80, totalTokens:33112, cacheReadTokens:26496}` 也印证了这点。
  直接把 input 和 cache_read 相加会重复计算。
- 换个供应商可能是 Anthropic 口径（缓存与 input 分开），所以不写死：**逐行以
  `computed_total_tokens` 为裁判**，五个桶之和必须严格等于该行 total，据此判断缓存和推理是否
  已含在 input/output 里。两种形状都有单测。
- **体积大头在数据库之外**：最大会话的 `rollout/model-io-<id>.jsonl` 12 MB、artifacts 1.2 MB、
  图片缓存 0.8 MB，而库里的行不到 1 MB。所以体积 = 库内 message/part 字节 + 这四处按会话 id
  命名的文件。只数数据库会把 14.8 MB 的会话报成约 1 MB。

对账：Orrery 输出与 Python 直接查库、遍历文件的独立计算逐会话比对，token 总和、调用次数、
体积三项在 3 个会话上全部一致（9/9）。

### 格式要点（均来自本机真实数据，非源码推断）

| 项 | Claude Code | Kimi Code | DSH | Codex |
|---|---|---|---|---|
| token 来源 | assistant 行 `message.usage` | `usage.record` 事件 | `assistant/message` 事件 `data.usage` | `token_usage_record`（新版）+ `event_msg/token_count` |
| 重复/陷阱 | 流式按内容块拆行，同 `message.id` 重复 → 去重保留最后一行 | 无重复；`usageScope` = `turn` / `session`（后者是上下文压缩的独立调用，也计入） | 每次写入追加一个 zstd 帧，需连续解多帧；v0 与 v3 并存时是同一历史的两份，只读 v3 | `total_token_usage` 按进程累计、resume 清零 → 累加去重后的 `last_token_usage`；旧账本漏记上下文压缩 → 有 `token_usage_record` 的时段以它为准 |
| 输入字段语义 | 不含缓存 | 不含缓存 | `inputTokens` 不含缓存 | `input_tokens` **含**缓存命中，需减 `cached_input_tokens` |
| 子 agent | `<id>/subagents/*.jsonl` | `agents/agent-N/` | 未见（`delegationDepth` 均为 0） | `session_meta.source.subagent` + `parent_thread_id`（guardian 自动审查） |
| 工作目录 | 行内 `cwd`（目录名编码有损，仅兜底） | `state.json.cwd`，旧版为 `workDir`，再兜底 `workspaces.json` | 首行 `session` 事件的 `cwd` | `session_meta.cwd` |
| 标题 | 首条非 `<` 开头的用户消息 | `state.json.title` | 最后一条 `session/title` | `session_index.jsonl` 的 `thread_name`，无则首条真实用户输入（跳过注入的 `<environment_context>` / `# AGENTS.md`） |
| 敏感字段 | — | `state.json.lastPrompt` 可能含粘贴的密钥，不读取 | `.credentials.yaml` 不读 | `auth.json` / `secrets/` 不读 |

**DSH 校验**：`storages/session_projcache` 是 DSH 自己的投影缓存，会落后于日志。截至缓存 `seq` 的事件累加与缓存 `tokenUsage.totals` 三项完全一致；日志更新，以日志为准。
**Codex 校验**：9 个 rollout 出现 `total_token_usage` 回落（resume 后清零，不重放旧记录）。无回落的文件里 `last` 累加 = 最终 total；12 个同时有两本账的文件 8 个完全一致，其余 4 个 `token_usage_record` 恰好多 3 次调用 = 上下文压缩。0.147/0.148 alpha 的 39 条记录只有 `total_tokens`、分项全 0 → 记为 `unsplit`。

**CC token 校验**：会话里的 `cost-state` 是 Claude Code 官方记账，但**按进程统计、resume 后清零**，且含标题生成/分类器等不进 transcript 的旁路调用。去重算法在同一进程区间内与之三项逐字节一致；跨进程总量只能从 transcript 求和，比官方少旁路调用那 1–5%。
## WorkBuddy 的口径（2026-09-27）

WorkBuddy 是腾讯的桌面应用（`~/.workbuddy`；`providerData.agent` 的值仍是 `"cli"`，
说明和 CodeBuddy CLI 同源，但 item 形状不一样，所以单独一个 adapter）。落盘位置：

`~/.workbuddy/projects/<压缩工作目录>/<sessionId>.jsonl`，一行一个 item。

- item 的 `type`：`session-meta` / `message` / `function_call` / `function_call_result` /
  `reasoning` / `file-history-snapshot` / `ai-title`
- **`cwd` 直接写在每个 item 上**，所以项目路径是精确的，不像 Claude Code 要解有损目录名
  （WorkBuddy 自己把盘符写成小写，显示时还原成大写）
- **标题取 `ai-title` 那条的 `aiTitle`**——WorkBuddy 自己生成的标题，比"最近一条用户输入"可靠
- 用户消息里会被塞进一整个 `<system-reminder>` 上下文块（OS/主题/工作目录…），
  那不是用户写的输入，标题和摘要都要跳过
- **用量按 `providerData.messageId` 去重**：一次请求会拆成 message / function_call /
  reasoning 多个 item，共用同一个 messageId 和同一份用量。实测 33 条带用量的 item 对应 33 个
  不同的 messageId，正常不重复；去重只是防流式重写
- 用量字段：`message.usage`（`input_tokens`/`output_tokens`/`total_tokens`）与
  `providerData.rawUsage`（`prompt_tokens`/`completion_tokens`/…）都读。**实测本机这家供应商
  是 OpenAI 口径：`input + output` 恰好等于 `total`，缓存已含在 input 里**，所以缓存桶丢掉、
  `unsplit = 0`；换成 Anthropic 口径的供应商时分项之和小于 total，差额进 `unsplit`
- `model` 取 item 上的 `providerData.model`（实际服务的模型）；`~/.workbuddy/workbuddy.db`
  的 `sessions.model` 是用户选的别名（如 `balanced-model`），两者不同，Orrery 显示前者
- 正在运行的会话登记在 `~/.workbuddy/sessions/<pid>.json`（pid / sessionId / kind=interactive），
  与 Claude Code 的 `~/.claude/sessions/<pid>.json` 同一套路，复用 `guard::pid_alive` 判活
- `workbuddy.db` 还有 `sessions` / `session_usage` / `workspaces` 表，其中 `sessions` 是会话的
  权威元数据（title / status / custom_title / model / context_window / transport），
  `session_usage` 记的是上下文窗口占用与 credit。当前 adapter 只读 jsonl，
  要补「用户改过的标题」「云会话」这类信息时才需要动它
- **删除未开放、恢复不做**：WorkBuddy 是 Electron 桌面应用，会话由它自己写，没有可供终端
  调用的 CLI
- 逐会话对账脚本：`scripts/verify-workbuddy.mjs`（直接只读本机真实数据，与 WorkBuddy 自己的 SQLite 索引和独立调用求和对照；不输出私人标题或路径）

索引：共用 `~/.orrery/index.json` 持久化解析缓存，按文件长度与 mtime 签名决定是否重解析。调用次数也按去重后的 messageId 累加；这次修正后索引版本升为 5，让旧缓存重建。

## 删除会话（2026-09-15）

实现：`src-tauri/src/adapters/cleanup.rs`，命令 `plan_delete`（只预览）/ `delete_sessions`（执行）。

### 安全约束

1. 前端只传 `(harness, id)`，路径由后端解析；id 只允许字母数字 `-` `_`；每个目标按真实路径校验必须在该 harness 根目录内
2. 10 分钟内有写入、或 `~/.claude/sessions/<pid>.json` 登记且进程存活的 CC 会话，拒绝删除
3. 执行时后端重新规划，不采信早先的计划；先删文件，全部成功后才改索引
4. 改索引前备份到 `~/.orrery/backups/<时间戳>/<harness>/`；写入 = 同目录临时文件 + rename；JSON 用 `serde_json` 的 `preserve_order` 保持键顺序与缩进风格
5. Orrery 不直接写其他工具的数据库。Codex sqlite 只经官方 `codex delete --force <uuid>`（`CODEX_HOME` 指向解析出的根目录）
6. Kimi / Codex 进程在运行时给出警告（可能把删掉的索引条目写回），不阻止

### 各工具实测结论

| 工具 | 删除的文件 | 索引 | 验证 |
|---|---|---|---|
| Claude Code | `projects/<p>/<id>.jsonl`、`projects/<p>/<id>/`、`file-history/<id>/`、`session-env/<id>/`、`tasks/<id>/` | 无（`history.jsonl` 是输入历史，不动） | 沙盒 |
| Kimi Code | `sessions/<ws>/<id>/` | `session_index.jsonl` 行、`file-history/<ws>` 的 `sessions[]` | 沙盒 + `kimi session list --all --json` 删除前 2 条 → 删除后 1 条 |
| DSH | `sessions/<ws>/<id>/`、`storages/session_projcache/sessions/<id>.json` | `storages/workspace.json` 的 `sessionIds` / `archivedSessionIds` | 沙盒（未用 DSH 本体回读） |
| Codex | 该 id 所有 rollout + 以它为父的 guardian 子 agent rollout | `state_5.threads`、`thread_history_1` 内容副本（经 CLI）、`session_index.jsonl` | 沙盒：`codex delete` 删父会话会删 rollout / threads / thread_history / session_index，但**不删子 agent** → 逐个调用；rollout 已进回收站时仍能清库；id 不在库里时报错 → 自行删文件与 session_index |

### 端到端测试方法

调试构建支持 `ORRERY_HOME` 把主目录指向沙盒（发布构建忽略该变量），此时也忽略各工具自己的 `CODEX_HOME` 等环境变量，避免指回真实目录。沙盒数据：CC 合成、Kimi/DSH 复制最小的真实会话、Codex 复制真实 rollout 并换成新 UUID 后写进复制出来的 sqlite。测试前后对真实目录做文件数与索引哈希快照，确认未改动。

### 占用口径与删除范围一致

"列表显示的占用"必须等于"删除时实际移除的字节"，否则删除后的"释放量"会对不上。CC 的占用因此包含 `file-history/session-env/tasks` 下的同 id 目录，DSH 包含投影缓存。
